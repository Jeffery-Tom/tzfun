## 一、简历项目描述（直接复制改）

**项目名称**：TzFun 自营租车平台（Spring Boot 后端）
**角色**：核心后端开发（独立从 0 到 1 设计与落地）
**技术栈**：Spring Boot 4.1.2 · Java 21 · MyBatis（注解版）· MySQL 8 · Redis · JWT · BCrypt

**项目描述**：
对标神州租车自营模式，实现「门店/车型管理 → 时间窗库存 → 订单状态机 → 优惠券 → 支付 → 取还车」的完整业务闭环。重点解决了租车场景下的三大并发难题：库存超卖、订单状态错乱、支付回调重复记账。系统采用 JWT + ThreadLocal 自建鉴权体系，DB 为真相源、Redis 为加速层，统一以「条件更新 + 受影响行数」保证并发安全。

## 二、技术亮点（挑 3~4 条写进简历，每条都要求能展开讲）

### 1. 时间窗库存：Redis + Lua 原子占释，根治超卖
- **痛点**：同一门店同一车型同一天被多人同时预订，会出现「超卖」（库存扣成负数）。
- **方案**：每日库存以 `storeId:carTypeId:yyyy-MM-dd` 为 key 存 Redis；占用/释放封装进**单个 Lua 脚本**，脚本内「先遍历校验所有日期 cur>=need、再统一 DECRBY」，检查与扣减在同一原子操作内完成（Redis 单线程保证无竞态）。
- **兜底**：提供 `rebuildFromDb` 从订单表聚合重算 Redis 库存，DB 始终为真相源。
- **关键词**：Lua 原子性、超卖、单脚本、DB 兜底。

### 2. 订单状态机：条件更新替代「先查再改」，杜绝状态竞态
- **痛点**：订单在 PENDING→CONFIRMED→IN_USE→RETURNED→SETTLED 流转中，并发操作可能让状态跳错或重复推进。
- **方案**：用枚举 `OrderStatus` 定义合法流转表（ALLOWED）；每次状态变更执行 `UPDATE ... SET status=#{new} WHERE id=#{id} AND status=#{old}`，**受影响行数=0 即抛并发冲突**，而非先 SELECT 再 UPDATE。
- **连带保证**：下单占库存失败 → `release()` 补偿；取消/还车释放库存与车辆状态严格成对。
- **关键词**：状态机、条件更新、受影响行数=1、补偿。

### 3. 支付异步回调幂等：不重复确认、不重复用券
- **痛点**：真实支付网关会**重复推送**同一笔成功通知，若每次都确认订单/用券/记账，会造成重复。
- **方案**：`out_trade_no` 设唯一约束；`handleNotify` 先查「已支付则直接返回 SUCCESS」做幂等去重；订单确认用 `WHERE status=PENDING` 条件更新（重复确认行数=0 不报错）；用券 `WHERE status=0` 天然幂等，且对重复回调时「券已用」的异常 `try/catch` 吞掉，保证返回 SUCCESS。金额以**订单表权威值**比对，防篡改。
- **关键词**：幂等、唯一约束、异步回调、try/catch 幂等忽略。

### 4. 优惠券：防超发 + 防复用，金额精确
- **领券防超发**：先插 `user_coupon`（`user_id, template_id` 唯一索引拦重复领），再 `UPDATE ... SET claimed_count=claimed_count+1 WHERE id=#{id} AND claimed_count<total_count` 条件更新，行数=0 即「已领完」回滚。
- **用券防复用**：`UPDATE ... SET status=1 WHERE id=#{id} AND status=0`，第二次用同一张券影响行数=0 直接失败。
- **金额**：全程 `BigDecimal`，折扣券封顶 `max_discount` 且不超订单额，**禁 float/double**。
- **关键词**：唯一索引、条件更新防超发、WHERE status=0 防复用、BigDecimal。

### 5. 统一鉴权与越权防护（加分项，体现安全意识）
- JWT 签发/解析 + 自建 `LoginInterceptor` 校验 `Authorization: Bearer <token>`；用户信息存 `ThreadLocal`，`afterCompletion` 中 `remove()` 防内存泄漏。
- **水平越权防护**：操作订单/支付前校验 `order.userId == 当前用户`，否则 403——不只是登录就放行。

## 三、面试高频追问 + 标准答案要点（背熟）

| 面试官可能问 | 你要答到的点 |
|------|------|
| 为什么库存占释要用 Lua，不用分布式锁？ | 分布式锁有获取/释放开销且易死锁；Lua 在 Redis 单线程内原子执行，检查+扣减一步到位，无竞态且性能高。 |
| 状态机为什么不用「先查状态再改」？ | 查和改之间有时间窗，并发下两个请求都查到 PENDING 都去改，会重复推进；条件更新把判断和改动合一，行数=0 即知别人已改。 |
| 支付回调重复推了 3 次怎么办？ | 第 1 次正常处理；第 2/3 次查到已支付直接 SUCCESS；用券那步券已 status=1，`useCoupon` 会抛异常，但被 try/catch 吞掉（券已用正是期望态），最终仍返回 SUCCESS，绝不让网关无限重试。 |
| 优惠券怎么做到「总量 100 张绝不多发」？ | 唯一索引拦同一人重复领 + `claimed_count<total_count` 条件更新，两者并发下双重保险；行数=0 即回滚已插的行。 |
| JWT 和 Session 怎么选？ | JWT 无状态、适合前后端分离、不用服务端存会话；本项目的 ThreadLocal 只是请求内传递用户身份，请求结束即清。 |
| BigDecimal 为什么不能用 double？ | double 二进制浮点有精度误差（0.1+0.2≠0.3），金额必须用 BigDecimal 或 BIGINT 分。 |
| Redis 挂了系统还能用吗？ | 查可用车/下单占库存会失败；但 DB（静态资料、订单）正常。Redis 是加速层，DB 是真相源，提供 `rebuildFromDb` 恢复。 |

## 四、可演示的端到端流程（面试讲项目时串一遍）
1. 注册/登录 → 拿 JWT；
2. `POST /carType/available` 选车（读 Redis 时间窗库存，过滤已满日期）；
3. `POST /order` 下单（占库存 → 落库，失败补偿释放）；
4. `POST /coupon/claim` 领券 → `POST /order` 时用券抵扣（BigDecimal）；
5. `POST /pay/create` → 模拟网关 `POST /pay/notify` 回调（幂等确认订单 + 用券）；
6. `POST /order/pickup` / `/return` 取还车（还车释放库存）。
