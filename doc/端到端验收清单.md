# TzFun 阶段1 端到端验收清单

> 目的：不读代码也能照着点，把「用户认证 → 基础数据 → 库存 → 下单 → 优惠券 → 支付」整条链路跑通。
> 适用端口：**9070**（不是 8080）。DB 名：`tzfun`。Redis：默认 `localhost:6379`。

---

## 0. 开始前必读（3 个前提，少一个都跑不通）

| # | 前提 | 为什么 |
|---|------|--------|
| 1 | 项目已启动，监听 **9070** | 之前一直误传是 8080，真实端口在 `application.yml` 里是 9070 |
| 2 | **Redis 必须开着**（`localhost:6379`） | 下单/查可用车/支付都碰 Redis 每日库存；关了会 500 |
| 3 | **数据库表必须先建**（项目不自动建表） | `schema.sql` 不会被 Spring 自动执行，必须手动跑（见第 1 节） |

> ⚠️ 所有请求统一加 Header：`Authorization: Bearer <token>`（**Bearer 后面有空格**，漏了直接 401 未登录）。

## 2. 准备测试账号（拿 token）

注册接口只能建「租客(RENTER)」，管理员要手动提。

**① 注册一个租客账号（renter）**
```
POST http://localhost:9070/user/register
Content-Type: application/json
Body: {"username":"xiaoming","password":"123456","name":"小明"}
```
→ 期望 `{"code":"200",...}`

**② 注册并提权一个管理员账号（admin）**
```
POST http://localhost:9070/user/register
Body: {"username":"admin","password":"123456","name":"超管"}
```
然后进 MySQL 把它提成管理员，**再重新登录**（角色是登录时写进 token 的）：
```sql
UPDATE user SET role='ADMIN' WHERE username='admin';
```
```
POST http://localhost:9070/user/login
Body: {"username":"admin","password":"123456"}
```
→ 返回 `data.token` = **admin_token**（复制备用）

**③ 租客登录拿 renter_token**
```
POST http://localhost:9070/user/login
Body: {"username":"xiaoming","password":"123456"}
```
→ 返回 `data.token` = **renter_token**

**Apifox 省力技巧**：在「环境/全局参数」里设
- `BASE_URL` = `http://localhost:9070`
- `Authorization` = `Bearer <renter_token>`（测写接口时临时换成 admin_token）

## 3. 端到端主流程（按顺序点，别乱序）

### 路径 A：纯状态机（不测支付，最简单，先跑这个）
顺序：下单 → 确认 → 取车 → 还车 → 结算

| 步骤 | 方法 / URL | Body 或参数 | 期望 |
|------|-----------|------------|------|
| 1 下单 | `POST /order` | `{"storeId":1,"carTypeId":1,"startTime":"2026-11-05T09:00:00","endTime":"2026-11-07T18:00:00"}` | `code:200`，**记下 `data.id`** |
| 2 确认 | `POST /order/confirm?orderId=<id>` | — | `code:200` |
| 3 取车 | `POST /order/pickup?orderId=<id>` | — | `code:200` |
| 4 还车 | `POST /order/return?orderId=<id>&mileage=300&damaged=false` | — | `code:200` |
| 5 结算 | `POST /order/settle?orderId=<id>` | — | `code:200` |

> 时间字段是 **`LocalDateTime`**（带 `T` 和时分秒），不是纯日期；门店/车型用种子里的 `storeId=1`/`carTypeId=1` 即可。

### 路径 B：带支付（完整含支付幂等，推荐也跑一遍）
顺序：**下单 → 创建支付 → 模拟支付回调 → 取车 → 还车 → 结算**

| 步骤 | 方法 / URL | Body 或参数 | 期望 |
|------|-----------|------------|------|
| 1 下单 | `POST /order` | 同上 | `code:200`，记 `data.id` |
| 2 创建支付 | `POST /pay/create?orderId=<id>` | — | `code:200`，返回含 `out_trade_no` 的字符串 |
| 3 模拟回调 | `POST /pay/notify`（**此接口免 token，网关回调无需登录**） | `{"orderId":<id>,"outTradeNo":"<上面返回的out_trade_no>","amount":<应付金额>,"tradeStatus":"SUCCESS"}` | 返回纯文本 **`SUCCESS`**（不是 JSON） |
| 4 取车 | `POST /order/pickup?orderId=<id>` | — | `code:200` |
| 5 还车 | `POST /order/return?orderId=<id>&mileage=300&damaged=false` | — | `code:200` |
| 6 结算 | `POST /order/settle?orderId=<id>` | — | `code:200` |

> ⚠️ **顺序陷阱**：`/pay/create` 要求订单是 `PENDING`。所以**先创建支付、再走回调完成确认**，不要先调 `/order/confirm` 再创建支付（那样状态已变 CONFIRMED，create 会报 400）。路径 A 和路径 B 的「确认」二选一即可。

**`/pay/notify` 的 `amount` 怎么填**：路径 B 第 2 步返回的字符串里有「应付=XXX」，把它原样填进 `amount`（如 `1000.00`）。金额对不上会返回 `FAIL`（防篡改）。

## 4. 优惠券用例（可选，路径 B 的增强）

> 优惠券**没有独立的"使用"按钮**：建模板靠 SQL 种子（已建好），使用只在支付回调里内部触发。

| 步骤 | 方法 / URL | 参数 | 期望 |
|------|-----------|------|------|
| 1 看可领券 | `GET /coupon/listTemplates` | — | 返回 3 张示例券，**记 `data[0].id`（templateId）** |
| 2 领券 | `POST /coupon/claim/<templateId>` | 路径参数 | `code:200` |
| 3 看卡包 | `GET /coupon/myCoupons` | — | 返回刚领的券，**记 `data[0].id`（userCouponId）** |
| 4 用券 | 在 **第 3 节路径 B 第 3 步** 的 `/pay/notify` Body 里加 `"couponId":<userCouponId>` | — | 返回 `SUCCESS`；再查 `myCoupons` 该券应消失（已用） |

> ⚠️ **已知小缺陷（如实告知）**：当前版本用券后，订单的 `discount_amount`/`pay_amount` **不会自动扣减**（支付回调只把券标记为已用，没把折扣金额写回订单）。所以你测到「券消失了但订单金额没变」属于这个集成点还没补全，不是你操作错。可后续让 CC 在 `handleNotify` 里补 `calcDiscount` + 回写订单金额。

## 5. 边界 / 异常用例（验收点，挑着点）

| 场景 | 操作 | 期望 |
|------|------|------|
| 非管理员建门店 | 用 **renter_token** `POST /store` | `code:403` |
| 无 token 访问 | 不带 Authorization `GET /user/info` | `code:401` 未登录 |
| 篡改 token | 把 token 改一位 `GET /user/info` | `code:401` |
| 非法状态跳步 | 对 PENDING 订单直接 `POST /order/return` | `code:400`「订单非使用中」 |
| 越权 | 用另一个租客的 token 操作别人的 orderId | `code:403` 无权操作他人订单 |
| 支付幂等 | 对同一个 orderId/outTradeNo **连发两次** `/pay/notify` | 两次都返回 `SUCCESS`（第二次不报错） |
| 重复领券 | 对同一 templateId 连点两次 `POST /coupon/claim` | 第二次 `code:400`「已领取」或「已领完」 |
| 取消释放库存 | 对 PENDING 订单 `POST /order/cancel` | `code:200`；之后该时段 `/carType/available` 容量恢复 |

## 6. 排错速查（返回异常时对照）

| 现象 | 原因 | 解决 |
|------|------|------|
| `code:500`，msg 含 `Unable to connect to Redis` | Redis 没开 | 启动 Redis（`redis-server`，默认 6379） |
| `code:500`，msg 含 `Table 'tzfun.xxx' doesn't exist` | 漏跑建表 SQL | 回到第 1 节把 3 个 SQL 跑完 |
| `code:400`，「开始日期/结束日期不能为空」 | 字段名错 | 下单用 `startTime`/`endTime`；查可用车用 `start`/`end`（不是 startDate/endDate） |
| `code:401` 未登录 | 漏 `Bearer ` 前缀或 token 失效 | Header 加 `Bearer ` + 空格；token 是登录时签发的，改角色/过期要重登 |
| `code:400`「订单状态不可支付」 | 先 confirm 再 create pay | 按路径 B 顺序：先 createPay（PENDING）再回调 |
| 连接被拒 / 无响应 | 服务没起或端口错 | 确认服务起在 **9070**，不是 8080 |

## 7. 当前版本已知小缺陷（非阻塞，留待阶段2）

1. **用券不回写订单金额**（第 4 节已说明）——`handleNotify` 只标记券已用，未调用 `calcDiscount` 写回 `discount_amount`/`pay_amount`。
2. `CarMapper.markAvailable` 非条件更新（`UPDATE car SET status='在库' WHERE id=?`，无 `AND status='出租中'`）——正常流程低风险，严格说应加条件。
3. `genOrderNo` 用时间戳+4位随机数，同一毫秒理论可能碰撞——简历项目够用，想严谨可换雪花算法。
