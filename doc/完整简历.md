## 项目经验

### TzFun 自营租车平台（Spring Boot + Spring Cloud 后端）

**角色**：核心后端开发（独立从 0 到 1 设计与落地）

**技术栈**：Java 21 · Spring Boot 4.1.2 · Spring Cloud 2025.1.3（Nacos / Gateway / OpenFeign / Sentinel）· MyBatis（注解版）· MySQL 8 · Redis（StringRedisTemplate + Redisson + Lua）· RocketMQ · JWT · BCrypt

**项目概述**：
对标神州租车自营模式，构建「门店/车型管理 → 时间窗库存 → 订单状态机 → 优惠券 → 支付(mock) → 取还车」完整业务闭环的后端系统。核心难点在于：租车资源在**时间维度上不可叠加**——同一辆车在不同日期属于完全不同的库存单元，并发下单极易出现重复占车与超租。围绕这一核心矛盾，按「单体验证 → 异步化 → 微服务化」三阶段演进：先用 Redis+Lua 原子占释库存、条件更新乐观锁解决并发；再引入 RocketMQ 做超时释放双保险与秒杀三层防超卖；最后拆分六个微服务并用 Gateway 统一鉴权、Outbox 实现跨服务最终一致。

**核心工作与亮点**：

1. **二维时间窗库存（Redis + Lua 原子占释，根治超卖）**
   每日库存按 `门店+车型+日期` 分槽存入 Redis，占用/释放封装进单个 Lua 脚本，脚本内「先遍历校验所有日期 `cur>=need`、再统一 DECRBY」，检查与扣减在同一原子操作内完成（Redis 单线程保证无竞态），并提供 DB 聚合重建兜底，DB 始终为真相源。

2. **订单状态机 + 支付回调幂等（条件更新替代「先查再改」）**
   状态流转用 `UPDATE ... SET status=#{new} WHERE id=#{id} AND status=#{old}`，受影响行数=0 即抛并发冲突；支付异步回调以 `out_trade_no` 唯一约束 + 已支付直接返回 SUCCESS 做幂等，金额以订单表权威值比对防篡改。

3. **RocketMQ 异步化：超时释放双保险 + 秒杀三层防超卖**
   超时未支付库存释放改为「延迟消息触发 + 定时任务兜底」双保险；优惠券秒杀以「Redis+Lua 预扣 + MQ 异步落库 + 唯一索引/条件更新」三层防超卖，明确「MQ 只做最终一致性补偿、不碰原子扣减」的职责边界。

4. **Spring Cloud 微服务化（阶段3）**
   按领域拆分 user / car / order / coupon / payment / gateway 六个服务，Nacos 服务发现、Gateway 统一鉴权（token 校验前移）、OpenFeign 跨服务调用，并以本地消息表（Outbox）+ 中继实现订单支付事件的最终一致性，保证跨服务消息不丢不重；秒杀库存分段 + Sentinel 限流兜底。

**量化成果（实测）**：

| 场景 | 并发 | 结果 |
|---|---|---|
| 优惠券秒杀 | 200 并发 / 100 库存 | 零超发（DB `claimed_count=100=total_count`、`user_coupon` 实发 100 条），错误率 0%，中位数响应 19ms、吞吐 236 QPS（本地单机） |
| 下单防重复 | 同一用户 100 并发 | 仅 1 单落库（DB 该时段订单数=1）、其余 99 全部拦截，零重复订单、错误率 0% |
| 支付最终一致（Outbox） | 100 次支付回调 | outbox_event 100/100 全部中继投递成功（status=1、积压 0），消费端幂等处理 100 条、订单 100 单全部 CONFIRMED |
| Feign 跨服务下单 | 端到端 | 定位并修复 LocalDate 参数编码不匹配导致的「该时段无车」真实 bug |

## 自我评价

- 独立从 0 到 1 完成一个可演示的微服务后端项目，覆盖认证、库存、订单、优惠券、支付五大领域，并主导技术选型与架构取舍。

- 重视量化验证：用 JMeter 压测产出真实数据，而非口头宣称「高并发」。
