## 1. 本模块目标（一句话）
mock 一个支付网关，重点演示真实支付最难的「**异步回调幂等**」：同一个支付成功通知被网关重复推多次，系统不能重复确认订单、不能重复用券、不能重复记账。

## 2. 引入什么
- 新建 `payment` 表（见 §4 DDL）。**本项目 MVP 用 mock 支付，不接真实微信/支付宝**；支付单核心字段 `out_trade_no`（商户订单号=幂等键）、`amount`、`status`、`pay_time`。
- 新建 `PaymentController`（`/pay/create`、`/pay/notify`）、`PaymentService`（`handleNotify`）、`PaymentMapper`。
- **不引入新中间件**；不碰 Redis（下单占库存已在模块4 完成，本模块只确认订单状态，不动库存）。

## 3. 关键实现（务必照此，红线不可破）

### 3.1 `POST /pay/create?orderId=`
- 校验订单存在且属当前用户（水平越权防护，复用 `OrderService.getOwnedOrder` 思路或自行校验 `user_id`）。
- 生成 `out_trade_no`（建议：订单号或 `PAY_` + 雪花/时间戳，必须全局唯一）。
- 落支付单：`status='未支付'`、`amount=订单应付额`（DECIMAL，从 order 表取 `pay_amount`）。
- 返回 mock 支付页/二维码占位（字符串即可）。

### 3.2 `POST /pay/notify`（异步回调，核心）
请求体带 `out_trade_no` / `orderId` / `amount`。处理逻辑（**幂等是重点**）：

```
handleNotify(dto):
  Payment p = paymentMapper.selectByOutTradeNo(dto.outTradeNo);
  if (p != null && p.status == 已支付) return "SUCCESS";   // 幂等去重：已处理过直接成功，绝不重复干活

  // 首次处理
  if (p == null) p = insertPayment(dto, 未支付);            // 落初始支付单
  金额校验：dto.amount 必须与 p.amount 一致，否则记录异常并返回 "FAIL"（防篡改）

  int n = orderMapper.updateStatus(dto.orderId, PENDING, CONFIRMED); // 防重复确认（条件更新）
  // 注意：订单可能已被手动 confirm 过（n==0），此时订单已是 CONFIRMED，属正常，不报错

  if (dto.couponId != null) {
    // 用券必须幂等：user_coupon 的 useCoupon 是 WHERE status=0 条件更新，
    // 重复回调时券已 status=1，再调会抛"券不可用"——必须用 try/catch 吞掉该异常，
    // 因为"券已用"正是期望终态，不能因此让 handleNotify 抛错导致网关反复重试。
    try { couponService.useCoupon(dto.couponId, dto.orderId); }
    catch (CustomException e) { /* 券已用（status!=0）属正常幂等，忽略 */ }
  }

  paymentMapper.markPaid(dto.outTradeNo);   // status=已支付, pay_time=NOW()
  return "SUCCESS";
```

### 3.3 红线（违反即打回）
1. **`out_trade_no` 唯一 + 已支付直接返回 SUCCESS** = 回调幂等（必做，不可妥协）。
2. 订单确认 `WHERE status=PENDING`（条件更新），受影响行数=0 不算失败（可能已被手动 confirm）。
3. 用券幂等：`useCoupon` 天然 `WHERE status=0` 幂等，但 `handleNotify` 必须 try/catch 其"券不可用"异常（见 §3.2）——否则重复回调会破坏幂等。
4. 金额 **DECIMAL**，禁 `double`/`float`；回调金额与支付单金额必须一致校验。
5. 水平越权：支付/创建支付单必须校验属于当前登录用户。

## 4. 建表 SQL（必须给出，项目不自动建表）
```sql
CREATE TABLE payment (
  id BIGINT AUTO_INCREMENT PRIMARY KEY,
  order_id BIGINT NOT NULL,
  out_trade_no VARCHAR(64) NOT NULL UNIQUE COMMENT '幂等键',
  amount DECIMAL(10,2) NOT NULL,
  channel VARCHAR(20) DEFAULT 'mock',
  status VARCHAR(20) NOT NULL COMMENT '未支付/已支付/失败/退款',
  pay_time DATETIME,
  create_time DATETIME DEFAULT CURRENT_TIMESTAMP
);
```

## 5. 复用与禁止
- 复用：`Result` / `CustomException` / `UserContext`（取当前用户）/ `OrderMapper.updateStatus`（条件更新，勿重写）/ `CouponService.useCoupon`（勿重写）。
- 禁止：重写已有类；引入 Redis/MQ；把金额写成 double/float。

## 6. 自测（完成后只做这些，贴证据）
1. 正常流程：`/pay/create` → `status=未支付`；`/pay/notify` 一次 → 订单转 `CONFIRMED`、券被用（若带 couponId）、支付单 `已支付`。
2. **重复回调**：对同一 `out_trade_no` 连续 `notify` 3 次 → 订单仍 `CONFIRMED`（不重复确认）、券仍只被用一次（不重复用）、支付单仍 `已支付`，且 3 次均返回 `"SUCCESS"`（不产生异常）。
3. 未支付订单保持 `PENDING`（不调 notify）。
4. 篡改金额：notify 的 `amount` 与支付单不一致 → 返回 `"FAIL"` 且状态不变。
