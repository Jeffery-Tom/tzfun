# TzFun 阶段2 开场指令（RocketMQ：异步化 / 超时释放 / 优惠券秒杀）

> 适用：阶段1（模块1~6）已全部完成并验收通过。本阶段引入 **RocketMQ**，做三件事：① MQ 基础设施打通；② 超时未支付自动释放库存（接住阶段1 留的口子）；③ 优惠券秒杀（阶段2 的高并发亮点）。
> 执行前请先 `Read` 根目录 `CLAUDE.md`（含省 Token 硬约定与项目结构速查），并 `Read` 本文件。禁止扫描整个 `src`、禁止读 `target/`、`*.jar`、本地仓库。

---

## 0. 阶段2 目标（来自架构规格 v1.0 §1.2 / §8 / §10，已冻结）

- **订单异步化 / 削峰**：支付成功后发领域事件，异步处理通知、账单等，解耦主流程。
- **超时未支付释放库存**：`PENDING` 订单超过 N 分钟未收到支付回调 → 自动 `CANCELLED` + 释放 Redis 时间窗库存 + 退回券。
- **优惠券秒杀**（节假日用车券）：Redis 预扣 + Lua 防超卖 + Sentinel 限流 + MQ 异步落库。

> **核心叙事（面试必讲，务必遵守）**：占车/用券的**原子性**永远交给 Redis+Lua（阶段1 已实现），MQ **只做异步、削峰、超时释放这种最终一致性补偿**。禁止用 MQ 做库存扣减。

## 1. 环境前提（必须，否则跑不起来）

- 本机安装并启动 **RocketMQ**（Windows 下先起 NameServer 再起 Broker）：
  - NameServer：`mqnamesrv.cmd`
  - Broker：`mqbroker.cmd -n localhost:9876 autoCreateTopicEnable=true`
- `application.yml` 增加 RocketMQ name-server 配置：`rocketmq.name-server: localhost:9876`。
- 引入依赖 `rocketmq-spring-boot-starter`（版本对齐 Spring Boot 4.1.2 兼容线，不确定时问用户或查官方兼容表）。
- Redis 仍须开着（超时释放要调 `RedisInventoryService.release`）。

## 2. 实施拆分（建议顺序，逐个自测后再下一个）

### 2.1 MQ 基础设施（地基，必须先通）
- 加依赖 + yml 配置 + 启动类加 `@EnableRocketMQ`（或 starter 自动装配）。
- 写一个最小闭环验证：一个 `Producer` 发一条测试消息到一个测试 Topic，一个 `Consumer`（`@RocketMQMessageListener`）收到并打印。**自测通过标准**：发得出、收得到。这一段纯粹打通管道，不接业务。
- 封装一个 `MqProducer` 工具类（发普通消息 + 发延迟消息两个方法），供 2.2/2.3 复用。

### 2.2 超时未支付释放库存（接住阶段1 的口子，优先级最高）
- **触发**：`OrderService.createOrder` 成功后（或 `PaymentController.createPay` 时），发一条**延迟消息**（RocketMQ 延迟等级，例如 15 分钟）到 Topic `order-pay-timeout`，body 带 `orderId`。
- **消费**：`OrderTimeoutConsumer` 收到后：先查订单，若仍为 `PENDING`（说明还没支付）→ 调 **已有的** `OrderService.cancel(orderId)`（它已包含：状态机 PENDING→CANCELLED 条件更新 + `RedisInventoryService.release` 释放时间窗库存 + 退券逻辑如有）。
  - ⚠️ 若 `cancel` 内部目前只释放库存、没退券，请顺手把"退券"补进 `cancel`（调用 `CouponService.returnCoupon`，若订单关联了 `coupon_id`）。阶段1 用券回写已完成，`orders.coupon_id` 已记录。
- **兜底（双保险，推荐）**：额外写一个 `@Scheduled` 定时任务（每小时或每 5 分钟），扫 `orders WHERE status='PENDING' AND create_time < NOW() - INTERVAL 15 MINUTE`，对未支付订单同样走 `cancel`。防止 MQ 消息丢失导致库存永不释放。
- **幂等**：`cancel` 本身是条件更新（行数=0 抛冲突），重复消费安全；定时任务重复扫也安全。
- **红线**：延迟消息 / 定时任务**只负责"发现超时 + 调 cancel 补偿"**，绝不自己直接 `DECRBY` Redis 库存（那是 Lua 的活）。

### 2.3 优惠券秒杀（高并发亮点）
区分**普通领券**（阶段1 已实现，DB 条件更新，低并发够用）与**秒杀领券**（本阶段新增）：
- **新接口**：`POST /coupon/seckill/{templateId}`（登录用户），与普通 `claim` 分开，避免影响现有逻辑。
- **Redis 预扣库存**：为秒杀模板在 Redis 维护 `seckill:stock:{templateId}`（初始化 = `total_count`）。写一段 **Lua 脚本**原子「判断 cur>=1 再 DECRBY」，返回 1/0（防超卖，与阶段1 占车同一套路）。
- **Sentinel 限流**：在秒杀接口加 Sentinel 资源 + 流控规则（QPS 阈值按量设，mock 项目给个合理值如 100），被限流返回「活动太火爆，请重试」。
- **MQ 异步落库**：Lua 预扣成功后，发 MQ 消息（带 userId + templateId），由 `SeckillCouponConsumer` 异步执行：`user_coupon` 插入（含 `(user_id,template_id)` 唯一索引兜底）+ `coupon_template.claimed_count + 1 WHERE < total_count` 条件更新。落库失败（如唯一索引冲突）回滚 Redis 预扣（INCRBY 退回）。
- **复用与一致**：金额 DECIMAL、条件更新 + 行数判断的统一叙事；秒杀券的 `coupon_template` 可复用现有表（加一个 `seckill` 标记字段或单独状态），不必新建表。
- 若 Sentinel 引入成本过高，至少保证「Redis Lua 预扣 + MQ 异步落库」两条骨架，限流作为加分项。

### （可选）2.4 订单异步化
- 支付成功（`PaymentService.handleNotify` 确认支付后）发领域事件到 Topic `order-paid`，Consumer 异步处理（发通知、记账单等）。本阶段若时间紧可后置，不影响 2.2/2.3 验收。

## 3. 架构红线（违反打回）

1. **占车/用券原子性 = Redis+Lua（已有），MQ 只做补偿**，禁止在 MQ Consumer 里直接扣 Redis 库存。
2. **金额一律 DECIMAL**，禁 float/double（秒杀券面额同理）。
3. **并发修改统一「条件更新 + 受影响行数=1」**（占车/用券/领券计数/改单状态），禁「先查再改」。
4. **超时释放必须幂等**（重复消费 / 定时任务重复扫都不出错）。
5. **复用阶段1 资产**：`Result`/`CustomException`/`UserContext`/`RedisInventoryService`/`OrderService.cancel`/`CouponService` 直接调，禁止重写。
6. 表结构变更（如 coupon_template 加 seckill 标记）须**同时给出建表/改表 SQL**（`doc/TzFun阶段1-模块5-SQL.sql` 追加 ALTER）。
